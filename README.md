# Бот-ознакомление лаборанта кабинета ИКТ

Консольное приложение на C++ (стандарт C++17), которое знакомит лаборанта
кабинета ИКТ с регламентом работы и проверяет усвоение материала.

## Возможности

### Базовая часть (СРС №1)

Интерактивное меню с пунктами 1-4 и 0:

1. Регламент рабочего времени (0,5 ставки = 20 часов в неделю).
2. Ежедневная проверка работоспособности ПО на ноутбуках до начала занятий.
3. Материальная ответственность за имущество класса.
4. Вся информация сразу.
0. Завершить ознакомление и перейти к контрольному вопросу.

В конце программа спрашивает: «Сколько часов в неделю обязан отрабатывать
лаборант на 0,5 ставки?» и повторяет вопрос, пока не будет введено `20`.

### Добавленные модули (СРС №2)

| Пункт меню | Модуль | Что делает |
|-----------|--------|------------|
| 5 | Учет рабочего времени | Запрашивает 5 рабочих дней, ставку 0.5 и часы в день. При 2 часах в день выводит предупреждение о дефиците времени и блокирует работу (цикл `do-while`), пока не подтверждена норма в 4 часа. |
| 6 | Дисциплинарные взыскания | Запрашивает номер ноутбука и выводит структурированную квалификацию инцидента: грубое нарушение трудовой дисциплины, саботаж учебного процесса, несоответствие занимаемой должности. |
| 7 | Протокол реагирования на саботаж | Последовательно выводит 5 шагов протокола с паузами через `std::this_thread::sleep_for`. |

Весь ввод проверяется: нечисловые значения не ломают программу, а запрос
повторяется.

## Сборка и запуск

```bash
g++ -std=c++17 -Wall -Wextra -pedantic main.cpp -o bot -pthread && ./bot
```

Ключ `-pthread` нужен для `<thread>`, остальные ключи включают
предупреждения компилятора; проект собирается без единого предупреждения.

## Пример работы модуля учета рабочего времени

```text
=== УЧЕТ РАБОЧЕГО ВРЕМЕНИ ===
Введите количество рабочих дней в неделю (5): 5
Введите ставку (0.5): 0.5
Введите количество рабочих часов в день (норма - 4): 2
Расчет: 5 дн. x 2 ч = 10 ч в неделю.

Ошибка! При 5-дневной рабочей неделе 2 часа в день составляют 10 часов в неделю.
Дефицит рабочего времени: 10 часов (50% от нормы 0.5 ставки).
Налицо факт предоставления заведомо ложных сведений работодателю.
Норма не подтверждена. Для продолжения необходимо подтвердить 4 часа работы в день.

Введите количество рабочих часов в день (норма - 4): 4
Расчет: 5 дн. x 4 ч = 20 ч в неделю.

Норма подтверждена: 5 дн. x 4 ч = 20 ч в неделю при ставке 0.5.
```

## Пример работы протокола реагирования

```text
=== ПРОТОКОЛ РЕАГИРОВАНИЯ НА САБОТАЖ ===
Введите номер ноутбука: 17

Шаг 1. Фиксация нарушения
Обнаружен факт неисполнения обязанностей: несанкционированный вынос оборудования (ноутбук №17),
...
Шаг 5. Административные последствия
Итог протокола: создание дисциплинарной комиссии, вынесение выговора, расторжение трудового договора
(0.5 ставки) и передача дела в органы материального учета ВУЗа.

Протокол завершен.
```

Между шагами выдерживается пауза 0,7 секунды.

## Code Review & Vulnerability Analysis

Проверялся код после СРС №1 и СРС №2 (состояние репозитория до коммитов `fix:`).
Методика: сборка с `-Wall -Wextra -pedantic`, отдельная сборка с
`-fsanitize=undefined`, затем запуск с «неудобными» вводами: пустые строки,
несколько значений в одной строке, огромные и отрицательные числа, обрыв
ввода (`Ctrl+D`), вывод через `|`. Каждая находка ниже **воспроизведена на
реальном запуске**, а после исправления проверена повторно.

| № | Проблема | Категория | Коммит с исправлением |
|---|----------|-----------|-----------------------|
| 1 | Обрыв ввода завершает программу с кодом «успех» | логика / надежность | `fix: exit with failure status when input ends before the briefing is finished` |
| 2 | Ввод по словам рассинхронизирует вопросы и ответы | логика / обход проверки | `fix: read whole input lines to keep prompts and answers in sync` |
| 3 | Нет диапазона для часов: переполнение `int` (UB) | безопасность / память | `fix: validate daily hours range to prevent integer overflow` |
| 4 | Номер ноутбука без верхней границы | валидация / бизнес-логика | `fix: validate laptop number against cabinet size` |
| 5 | Шаги протокола не видны из-за буферизации | надежность / UX | `fix: flush output before protocol delays` |

### 1. Обрыв ввода завершает программу с кодом «успех»

**Описание проблемы:**
При конце входного потока (EOF) функции `readInt()` и `readRate()` печатали
сообщение и вызывали `std::exit(0)`. Код `0` означает «программа
отработала успешно», хотя контрольный вопрос не пройден.

**Тестовый ввод и поведение:**

```bash
printf '0\n' | ./bot > /dev/null; echo $?     # до исправления: 0
```

Пользователь выбрал «0. Завершить ознакомление», но на контрольный вопрос
не ответил. Для оболочки, скрипта или системы учета это выглядит как
успешное прохождение.

**Потенциальные последствия:**
Если бот запускается автоматически (скрипт ознакомления сотрудников, LMS,
обёртка с проверкой кода возврата), любой обрыв ввода (закрытое окно,
потерянное SSH-соединение, `Ctrl+D`) будет записан как «лаборант
ознакомлен». Это нарушает главную цель бота: сотрудник не ответил
на контрольный вопрос, но в отчете числится прошедшим.

**Предлагаемое решение:**
Единая функция остановки с ненулевым кодом и сообщением в поток ошибок:

```cpp
[[noreturn]] void stopOnEndOfInput()
{
    std::cerr << "\nВвод завершен до окончания ознакомления. "
                 "Программа остановлена.\n";
    std::exit(EXIT_FAILURE);
}
```

**Что сохранено (Don't throw the baby out with the bathwater):**
Меню, вопросы и блокировки не изменены. При обычной работе код возврата
по-прежнему `0`, а при EOF он равен `1`. После исправления:
`printf '0\n' | ./bot > /dev/null 2>&1; echo $?` выводит `1`.

### 2. Ввод по словам рассинхронизирует вопросы и ответы

**Описание проблемы:**
Ввод читался как `std::cin >> token`, то есть по одному слову. Всё, что
пользователь написал в строке после первого слова, остается во входном
буфере и становится «ответом» на следующий вопрос, который он еще
не видел.

**Тестовый ввод и поведение (до исправления):**

```text
0 20
```

```text
Переходим к контрольному вопросу.

Сколько часов в неделю обязан отрабатывать лаборант на 0,5 ставки?
Правильно! Ознакомление завершено.
```

Одна строка выбрала пункт «0» и сразу же ответила на контрольный вопрос.
Так же строка `5 5 0.5 2 4` в меню целиком проходит модуль учета
времени, включая блокировку, а строка `abc def` порождает две ошибки
вместо одной.

**Потенциальные последствия:**
Контрольный вопрос и блокировка по часам нужны, чтобы человек
осознанно подтвердил норму. Вставкой готовой строки (или автозаполнением
в терминале) их можно пройти, не прочитав ни одного вопроса. Для
дисциплинарного процесса это серьезно: «подтверждение нормы в 4 часа»,
которое пользователь не видел, не имеет ценности.

**Предлагаемое решение:**
Читать строку целиком и принимать ее, только если вся строка является
одним числом:

```cpp
std::string readLine(const std::string& prompt)
{
    std::cout << prompt;

    std::string line;
    if (!std::getline(std::cin, line))
    {
        stopOnEndOfInput();
    }
    return line;
}

// в readInt():
std::istringstream parser(readLine(prompt));
int value = 0;
char trailing = 0;
if (parser >> value && !(parser >> trailing)) { return value; }
```

**Что сохранено:**
Ввод `20`, ` 20 ` (с пробелами) и строки с `\r\n` принимаются как раньше.
После исправления `0 20` дает «Ошибка! Введите целое число.», а вопрос
задается только после отдельного ввода `0`.

### 3. Нет диапазона для часов: переполнение `int` и бессмысленные расчеты

**Описание проблемы:**
Количество часов в день проверялось только на равенство `4`. Любое
другое целое число принималось в расчет `workDays * hoursPerDay`
без проверки диапазона.

**Тестовый ввод и поведение (до исправления, вывод сокращен):**

```text
Часов в день: 2000000000
Расчет: 5 дн. x 2000000000 ч = 1410065408 ч в неделю.

Часов в день: -3
Расчет: 5 дн. x -3 ч = -15 ч в неделю.

Часов в день: 25
Расчет: 5 дн. x 25 ч = 125 ч в неделю.
```

Сборка с `-fsanitize=undefined` подтверждает:
`runtime error: signed integer overflow: 5 * 2000000000 cannot be
represented in type 'int'`. Это неопределенное поведение (UB), а не просто
«странный результат».

**Потенциальные последствия:**
Модуль учета времени строит на этих числах обвинение в «заведомо ложных
сведениях» и дефиците часов. Отрицательные и невозможные значения
(более 24 часов в сутки) дают абсурдные расчеты, а при UB компилятор
вправе сгенерировать любой код, особенно при оптимизации. Результат
расчета времени сотрудника не должен зависеть от того, как собрана
программа.

**Предлагаемое решение:**
Проверять диапазон до вычисления:

```cpp
constexpr int MAX_DAILY_HOURS = 24;

if (hoursPerDay < 1 || hoursPerDay > MAX_DAILY_HOURS)
{
    std::cout << "Ошибка! Количество часов в день должно быть "
                 "от 1 до " << MAX_DAILY_HOURS << ".\n";
    continue;
}
const int weeklyHours = workDays * hoursPerDay;
```

**Что сохранено:**
Сценарий по ТЗ не менялся: `2` часа дают предупреждение о дефиците,
`3` часа дают «Норма не подтверждена», `4` часа подтверждают норму.
Цикл блокировки остается `do-while`; `continue` переходит к его условию.
С UBSan после исправления ошибок `runtime error` нет.

### 4. Номер ноутбука без верхней границы

**Описание проблемы:**
Модули «Дисциплинарные взыскания» и «Протокол реагирования» проверяли
только `номер > 0`, а код проверки был скопирован в обоих местах.

**Тестовый ввод и поведение (до исправления):**

```text
Введите номер ноутбука, вынесенного из кабинета: 2147483647
Инцидент: самовольный вынос учебного настроенного ноутбука №2147483647
```

**Потенциальные последствия:**
Программа формирует документ о грубом нарушении дисциплины по ноутбуку,
которого не существует. Опечатка (`177` вместо `17`) не будет замечена,
и служебная записка уйдет заведующему кафедрой и декану с неверными
данными. Такое основание для выговора или увольнения легко оспорить,
а проверка записей камер (шаг 3 протокола) будет искать несуществующее
устройство.

**Предлагаемое решение:**
Одна общая функция с верхней границей, которая заодно убирает дублирование:

```cpp
constexpr int LAPTOP_COUNT = 30; // число ноутбуков в кабинете ИКТ

int readLaptopNumber(const std::string& prompt)
{
    int laptopNumber = 0;
    do
    {
        laptopNumber = readInt(prompt);
        if (laptopNumber < 1 || laptopNumber > LAPTOP_COUNT)
        {
            std::cout << "Ошибка! В кабинете ноутбуки с номерами от 1 до "
                      << LAPTOP_COUNT << ".\n";
        }
    } while (laptopNumber < 1 || laptopNumber > LAPTOP_COUNT);
    return laptopNumber;
}
```

**Что сохранено:**
Тексты модулей и пример из ТЗ (ноутбук №17) работают без изменений.
Значение `LAPTOP_COUNT = 30` нужно заменить на реальное число ноутбуков
в кабинете; оно хранится в одном месте.

### 5. Шаги протокола не видны из-за буферизации вывода

**Описание проблемы:**
Модуль 3 должен создавать «эффект реального времени» с паузами
`std::this_thread::sleep_for`. Но если стандартный вывод не подключен
к терминалу (`|`, перенаправление в файл, некоторые консоли IDE),
библиотека накапливает текст в буфере и выдает его целиком только
в конце.

**Тестовый ввод и поведение (до исправления):**

```bash
printf '7\n17\n0\n20\n' | ./bot | ... # время появления строк «Шаг N»
19.073 Шаг 1. Фиксация нарушения
19.076 Шаг 2. Уведомление руководства
19.080 Шаг 3. Проверка доказательной базы
19.083 Шаг 4. Подача служебной записки
19.086 Шаг 5. Административные последствия
```

Все пять шагов появились за 13 миллисекунд, хотя программа «спала»
около 2,8 секунды.

**Потенциальные последствия:**
Проверяющий запускает код на своей машине, и если вывод буферизуется, то
программа выглядит зависшей, а затем выдает всё сразу. Пользователь
прерывает процесс (`Ctrl+C`), так и не увидев шаги 4-5
(служебная записка и административные последствия). Если вывод пишется
в журнал, временные метки шагов тоже теряют смысл.

**Предлагаемое решение:**
Сбрасывать буфер перед каждой паузой:

```cpp
void pauseBetweenSteps()
{
    std::cout << std::flush; // показать шаг до паузы
    std::this_thread::sleep_for(
        std::chrono::milliseconds(PROTOCOL_STEP_DELAY_MS));
}
```

**Что сохранено:**
Тексты шагов, их порядок и длительность пауз не менялись. После
исправления шаги появляются с интервалом около 0,7 с:
`13.132`, `13.832`, `14.531`, `15.232`, `15.932`.

## Вывод

Найдено и исправлено пять реальных проблем: три из них позволяют
обойти или обесценить проверки бота (1, 2, 4), одна приводит к
неопределенному поведению (3), одна ломает «режим реального времени»
протокола (5). Каждое исправление сделано отдельным коммитом, а
меню, контрольный вопрос, блокировка по часам и протокол работают
по-прежнему: рабочая логика сохранена, исправлены только слабые места.
